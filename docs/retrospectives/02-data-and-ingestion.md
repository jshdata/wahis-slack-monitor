## RET-DATA-01 — JOIN 결과가 맞아 보여도 발생 건수는 늘어날 수 있었다

**상태: 해결, 통계 단위의 한계는 유지 / 근거: 이전 기록, 현재 SQL.**

Report 수는 발생 건수가 아니다. Event에 여러 Report가 있고 각 Report에서
같은 발생지가 다시 등장한다. `event_id`로 두 테이블을 단순 JOIN하면 하나의
발생지가 후속 보고서 수만큼 늘어날 수 있었다.

국가·질병 메타데이터는 이벤트당 한 번만 쓰고, 발생 건수는
`COUNT(DISTINCT outbreak_id)`로 집계하는 방향으로 정리했다.
누적 정량값도 후속 보고서마다 더하면 안 된다. 예를 들어 total 10·15·18의 최종 누계는
18이지 합계 43이 아니다. 신규·누계와 ID·동물 수의 의미를 먼저 정해야 했다.

현재 통계는 고유 ID 단위다. `cluster_count > 1`인 집단발생의 구성 단위 수를
합산하는 지표와는 다를 수 있다. 같은 농장이나 좌표의 고유 수와도 동일한 개념이 아니다.
모든 이벤트의 공식 수치와 ID 수가 일치한다고 일반화하지 않는다.

근거: [통계 SQL](../../database/stats_db.py), [대시보드](../../database/dashboard_db.py).

## RET-DATA-02 — 구현한 Episode 판정을 운영에 넣지 않기로 했다

**상태: 운영 제외·보류 / 근거: 사용자 제공 이전 기록, 로컬 분석 파일.**

신규 보고가 많아지면서 전문가가 먼저 볼 변화를 선별하고 싶었다.
약 13만 건의 발생지 자료를 CSV로 추출하고 Tableau로 탐색했다는 기록이 있다.
국가·질병별 발생 간격이 크게 달라 최초 관측 이전 기간까지 0으로 채우는 접근을
보류했다. 기록 없음과 발생하지 않음을 동일하게 취급하지 않으려는 판단이었다.

28일 간격으로 Episode를 나누고 FIRST_OCCURRENCE·CONTINUING·RECURRENCE를
구분하는 분석을 시도했다. Finland 사례에서 같은 Event를 과거 조회에서 제외하면
같은 이벤트 안의 이전 발생까지 사라져 첫 발생으로 잘못 판정한다는 문제를 발견했다.
Argentina 사례에서는 non-poultry 질병명 접미사 때문에 exact match도 실패했다.
이전 기록에는 이들 수정과 실제 Slack 시험까지 남아 있다.

그러나 **발생 간격으로 만든 분석상 Episode와 WAHIS 공식 Reason은 의미가 다르다.**
28일 기준으로 공식적인 첫 발생·재발을 대신 판단할 근거가 부족했다.
기능을 구현했다는 이유로 운영에 연결하지 않고, 알림은 공식 Reason을 번역·강조하는
방향으로 바꿨다. 발생 빈도·공간 범위·피해 규모의 이상징후 분석은 구상·탐색 단계다.
운영 탐지 모델을 완성하거나 전문가 판단을 자동화한 것으로 기록하지 않는다.

Episode 관련 로컬 파일이 있다는 사실과 GitHub에 배포됐다는 사실도 구분한다.
근거: [Reason 표시](../../slack/notifier.py),
[ddc0e3b](https://github.com/jshdata/wahis-slack-monitor/commit/ddc0e3b).

## RET-DATA-03 — 보고서의 isWild를 발생지에 대입할 수 없었다

**상태: 구현·일부 검증 완료, 전체 과거 적재 진행 중 / 근거: 원본 API·DB 대조.**

처음에는 `report_quantitative.is_wild`가 있으니 발생지까지 분류할 수 있다고
생각하기 쉬웠다. 그러나 이 값은 보고서·동물종 정량자료에 연결되어 있어
한 보고서에 사육·야생 발생지가 함께 있으면 개별 `outbreak_id`의 구분을 대신할 수 없다.
이 가정을 사용자의 지적 이후 명확히 철회했다.

종 이름에 `wild`·`domestic`이 있는지도 확인했다. 당시 12,114개 정량자료 행 중
11,331행(약 93.5%)에는 둘 다 없었다. `Domestic cat`이면서 is_wild=1인 기록도
확인했다. 이름에 표현이 없다고 사육으로 간주할 수 없었다. 이 숫자는 발생 건수가 아니라
정량자료 행 수라는 점도 함께 정정했다.

발생지 상세 조회 경로를 찾고 실제 응답에서 확인했다.

```text
/api/v1/pi/review/report/{report_id}/outbreak/{outbreak_id}/all-information
speciesQuantities[].totalQuantities.isWild
```

실제 ID 198522·198516의 Wild boar는 true, 198473의 Birds는 false였다.
이 근거로 `outbreak_species`에 종 ID·이름·is_wild를, `outbreaks`에
사육·야생·혼합·미확인 분류를 저장했다. HPAI 가금/가금 외와 사육/야생은 별개로 유지했다.
`wildType` 전체 선택지와 사육 중인 야생종 등의 세부 상태는 아직 검증하지 않았다.

근거: [발생지 API](../../wahis/detail_api.py), [저장·분류](../../database/outbreak_species_db.py),
[적재 가이드](../outbreak-species-loading.md).

## RET-DATA-04 — 긴 적재를 한 번에 성공시키기보다 나누어 재개하게 했다

**상태: 구현·테스트 완료, 전체 데이터 완주는 진행 중.**

13만 건 이상을 한 번에 수집하면 실패나 작업 중단 후 다시 시작하는 비용이 컸다.
`--limit`, `--max-minutes`, 완료 보고서 버전과 수집 시각을 추가했다.
실패 건은 완료로 바꾸지 않고 다음 실행에서 다시 시도한다. 보고서 버전이 바뀐
발생지도 재수집한다. 오래된 응답이 최신 내용을 덮지 않도록 저장 직전 현재 버전을 확인한다.

한 발생지의 축종 행 교체와 분류·완료 표시를 하나의 트랜잭션으로 처리했다.
빈 동물종 목록은 unknown으로 완료하지만 응답 필드 누락은 실패로 남긴다.
처리 제한은 성공 수가 아니라 시도한 발생지 수다.

사용자 실행에서는 초기 10건 모두 성공·46.7초를 확인했다.
초기 코드가 DB 초기화 후에야 첫 로그를 출력해 실행 중인지 알 수 없는 문제도 있었다.
연결·스키마·건수 조회 단계 로그를 추가했다.
신규 기능에 전체 JSON 테이블을 추가했을 때에는 `--init-schema`를 하지 않아
1146 테이블 없음 오류가 발생했고 초기화 옵션으로 해결했다. 현재는 해당 JSON 테이블을 사용하지 않는다.

시간 제한은 진행 중 작업을 강제로 끊는 엄격한 deadline이 아니다.
Ctrl+C 후에도 진행 중 묶음의 재시도·저장을 마칠 때까지 기다릴 수 있다.
근거: [배치 코드](../../outbreak_species_load.py), [테스트](../../tests/test_outbreak_species.py).

## RET-DATA-05 — 병렬 요청의 이득과 병렬 저장의 충돌을 분리했다

**상태: 완화, 최종 구성의 장기 성능 확인 필요.**

순차 실행은 매 건 API 대기·DB 새 연결·1초 대기가 쌓였다.
HTTP 세션과 작업별 DB 연결을 재사용하고 기본 API 동시 작업을 3개로 늘렸다.
서버 429/503의 Retry-After를 반영해 과도한 재요청도 줄이도록 했다.

변경 후 사용자 실행에서 100건 모두 성공·256.3초(약 2.56초/건)를 확인했다.
초기 10건의 약 4.67초/건과 비교하면 개선됐지만 표본 크기와 네트워크 조건이 달라
정밀 벤치마크로 보지는 않는다.

이후 10건 실행에서 DB 1213 데드락이 3회 발생했다. 전부 재시도에 성공했으나
대기 시간이 추가됐다. 재시도 기본값을 5초에서 3초로 낮췄지만 이것만으로
충돌 원인을 줄이는 것은 아니었다. API 병렬은 유지하고 DB 저장을 한 번에 한 건으로
직렬화했다. 정확한 InnoDB 데드락 그래프를 수집하지 않았으므로 세부 잠금 원인은 미확정이다.

`ping(reconnect=True)` 사용 경고도 확인했다. `ping()` 실패 시 해당 연결을 폐기하고
재시도에서 새 연결을 만드는 방식으로 바꿨다.
테스트에서는 요청 병렬·DB 저장 비중첩·연결 재사용·실패 연결 교체를 확인했다.
운영 최종 구성의 전체 100건 벤치마크와 외부 프로세스 충돌은 별도 확인이 필요하다.
프로세스 내부 잠금이 다른 자동 수집 프로세스의 DB 작업까지 제어하는 것은 아니다.

중간 평균이 낮아진다는 관찰만으로 최종 속도를 확정하거나 반대로 사용자의 체감을
부정하지 않아야 한다는 소통상의 교훈도 남겼다. 오류 빈도와 총 처리 시간을 함께 본다.

근거: [작업 자원·저장 잠금](../../outbreak_species_load.py),
[13개 등 단계별 테스트 이력을 포함한 현재 테스트](../../tests/test_outbreak_species.py).

## RET-DATA-06 — 전체 JSON 보존을 구현했다가 용량 때문에 철회했다

**상태: 전체 보존은 운영 제외, 경량 적재로 전환 완료.**

발생지 API에 방역조치·진단 방법·생산 유형·생산 시스템·행정구역·동물종별 수치가
더 있다는 사실을 확인했다. 같은 API를 다시 요청하는 비용을 줄이려고 전체 응답을
`outbreak_detail_snapshots`에 JSON으로 저장하도록 한동안 구현했다.

하지만 당시 Aiven 화면은 1GB 중 56.7% 사용으로 약 433MB만 남아 있었다.
저장된 368개 응답의 평균 약 5.1KB를 전체 136,549개 발생지에 적용하면
JSON 본문만 약 664MiB(약 696MB)였다. 테이블·인덱스·운영 공간은 별도다.
`information_schema` 테이블 사용량 약 155MiB만 보고 디스크 여유를 판단할 수 없었다.

4개 실제 응답 압축 시험에서는 전체 규모를 gzip 약 198MiB, 발생지별 ZIP 약 216MiB로
추산했다. 표본이 작아 200~300MB 정도의 거친 예상일 뿐이었다.
이미 PDF 저장용 Railway Bucket 설정은 있었지만 이를 처음 확인하지 않고
새 설정처럼 안내한 오류도 있었다. 연결 코드를 먼저 확인해야 했다.

사용자는 Railway 쪽 500MB 한도와 기존 약 100MB 사용을 제약으로 설명했다.
이것이 Bucket·Volume 중 어느 자원에 적용되는지 콘솔로 독립 확인한 것은 아니다.
회고에서는 이를 서비스 전체의 보편적 요금제 한도로 단정하지 않는다.
제약을 받아들이고 당장의 목표인 축종·사육야생 구분만 DB에 남기기로 결정했다.

정리 전 로컬 gzip 백업을 생성하고 행 수와 압축 해제를 검증한 후,
축종 5,660행은 보존하면서 동물종 raw_json 컬럼과 전체 응답 433개 테이블을 제거했다.
기존 분류·완료 표시도 유지했다. 경량 코드의 실제 1건 적재 성공을 확인했다.
원본 JSON을 계속 Railway로 보내는 코드는 현재 구현·활성화되어 있지 않다.

전체 적재 후 추가 DB 용량은 당시 수십 MB~100MB 정도로 추정했을 뿐이다.
이미 삭제한 공간이 실제 디스크에서 얼마나 회수됐는지, 최종 추가 용량이 얼마인지는
운영 측정이 남아 있다. 임의의 기존 컬럼 삭제나 자동 OPTIMIZE TABLE은 하지 않았다.
저장하지 않은 추가 정보가 필요하면 초기 백업 범위 밖의 발생지는 API를 다시 조회해야 한다.

근거: [정리 도구](../../cleanup_outbreak_json.py), [현재 저장 필드](../../database/outbreak_species_db.py),
[저장 정책](../outbreak-species-loading.md). 로컬 백업 자체는 GitHub에 올리지 않는다.

## RET-DATA-07 — 과거 배치에만 있던 축종 수집을 공통 적재에 연결했다

**상태: 구현·커밋·푸시 완료, 실제 다음 자동 실행은 별도 검증 대상.**

기존 축종 배치는 다운로드 중이었지만 신규 자동 보고서 경로는 발생지 기본정보만 저장했다.
배치만 끝내면 이후 새 보고에서 다시 정보가 빠질 수 있었다.
`save_report_detail()` 안에 축종 수집을 넣어 `main.py`, `detail_initial_load.py`,
`backfill_disease.py`가 모두 같은 완료 조건을 사용하도록 했다.

이미 완료된 버전은 건너뛰고 현재 DB 보고서 버전을 조회해 과거 응답이 최신 내용을
덮지 않게 한다. 실패하면 보고서 완료 표시를 하지 않아 기존 복구로 이어진다.
공통 경로·재시도·질병 범위 관련 28개 테스트를 통과했다.

확장 확인 중 BSE 테스트 1개는 알림 enqueue가 추가된 상황에서 마지막 SQL을
기본 INSERT라고 가정해 실패했다. 기존 DB 코드로도 재현됐고 이번 기능의
통과 결과로 덮어 쓰지 않았다. 해당 기대값 수정은 남겨 두었다.

## RET-DATA-08 — ‘신규·갱신’과 ‘신규 발생’을 실제 37개 보고서로 검증했다

**상태: 이벤트 7176 검증 완료, 다른 이벤트로 일반화하지 않음.**

화면의 New/Updated outbreaks 합계와 고유 ID 수가 다르다는 질문에 대해
집단발생·감염 동물 수·보고일 차이를 설명하는 데 그치지 않고 원본을 대조했다.
현재 DB에 이 이벤트 Report 메타데이터가 일부만 있어 과거 Report 37개는 API로 조회했다.

라트비아 ASF 이벤트 7176에서 신규 ID 합계=638, 최신 원본 고유 ID=638,
DB 고유 ID=638으로 일치했다. 신규·갱신 합계 641에는 기존 ID 수정 3회가 포함됐다.
모든 연속 보고서의 추가 ID 집합도 신규 생성 ID 집합과 같았다.
최신 감염 동물 수는 1,601마리로 별개이며, 10월 20일 보고된 신규 8개 ID의 실제
발생일은 10월 12~18일이었다. 발생일 필터와 보고일 필터를 혼동하면 안 됐다.

이후 Slack·ntfy에 축종 이름·분류·혈청형/아형과 신규 발생 건수를 추가했다.
신규 건수는 `created_by_report_id=현재 report_id`의 고유 ID 수이며 갱신은 제외한다.
갱신만 있어도 보고서 알림을 보내고 0건으로 표시한다. 미완료 적재는 0 대신 미확인이다.
원본 조회에 실패해도 알림 자체를 막지 않고 확인 불가 상태로 전달한다.
